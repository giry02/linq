01 · REQUIREMENT TRACE

요구사항별 테이블 현황과 해결 방향

필드가 보인다는 이유만으로 구현 가능으로 판정하지 않음. 업무 식별자·상태·권한·시간 기준이 확인되어야 개발 가능으로 판정

요구사항현재 테이블·필드현황·문제점영향해결안 / 확인 필요
R-SVC-003사용자설정 가능 기간 안내

날짜 조회는 이벤트·운행 집계 테이블과 API query 사용. 테이블 명세에 화면별 최대 조회 기간 정책 없음

현재 프론트의 사용자설정에는 최대 기간 검증이 없고 서버 상한도 소스만으로 확인 불가. 31일은 원문 요구가 아님

임의의 31일 제한 시 장기 분석 업무를 막거나, 무제한 조회 시 대용량 테이블 부하 발생

결정 질문: 실제 업무에 필요한 최대 조회 범위, 서버 성능·데이터량·응답시간 기준 확인. 확정 후 API 정책과 프론트 안내를 동일 적용

R-SVC-006·007·009차량·엔진·배터리 오류 통합

TB_EVENT_ERROR, TB_EVENT_BM_ERROR, TB_EVENT_LI_ERROR, TB_EQUIPMENT_ERROR, TB_EQUIPMENT_ERROR_CODE

유사 이벤트가 원천별 테이블로 중복. 현재/과거·완료·중요도 의미가 서로 다르고 배터리/차량 구분도 API 표준 코드가 아님

중복 집계, 잘못된 완료 판단, 신규 오류 코드 오분류

통합 fault_event DTO와 sourceType(VEHICLE/ENGINE/BATTERY), lifecycleStatus, statusReason, severity 분리. 원천 테이블은 유지하되 API 통합 계층에서 표준화

R-SVC-008PDF 있을 때만 아이콘

TB_FILE: FILE_ID·SEQ·파일명·URI. 오류·정비 업무 객체와 문서 종류·언어·버전을 연결하는 명시적 관계 부족

FILE_ID가 있어도 실제 파일 존재·사용자 권한·언어 버전을 보장하지 못함

깨진 링크, 권한 우회, 잘못된 언어 매뉴얼 제공

fault_document 관계 추가: faultCode/eventId, documentKind, locale, version, storageKey, activeYn, accessPolicy. 목록 API는 downloadable과 documentId만 반환

R-MNT-001정비 이력 Claim 번호

TB_SERVICE_REPAIR_RESULT의 AUFNR(오더), QMNUM(통지), LINQ_NO와 TB_SERVICE_OCS의 ORDER_NO 확인. Claim 명칭 필드는 확인되지 않음

수리 ID·오더·통지·Claim의 업무 관계와 유일성이 미확정

임의 Claim 생성 시 SAP/서비스 정합성 훼손과 고객 오인

수리 ID가 Claim인지 업무 확인. 다르면 maintenance_external_identifier에 sourceSystem, identifierType, identifierValue, effectiveAt 추가 후 API 제공

R-MNT-002·005·006플릿/딜러 필드·조치 권한

TB_MENU, TB_MENU_ROLE, TB_COMPANY_MENU, TB_COMPANY_MENU_GROUP, TB_COMPANY_ROLE, TB_USER_ROLE

SITE_TYPE 정의가 테이블마다 다르고 DENY_ROLE_ID·GROUP_SET_LIST가 문자열 목록. UI 숨김만으로는 필드·API 보호 불가

직접 URL·API 호출로 제한 정보 노출 또는 조치 실행 가능

user_account·organization·role·permission·role_permission으로 통합. menu.view, maintenance.detail.view, supply.reset 같은 action 권한을 서버 DTO와 mutation에 적용

R-MNT-003·004정비 일시·완료 여부

TB_SERVICE_OCS·REPAIR_RESULT·SCHEDULE에 접수·등록·완료·결과 시각과 여러 Y/N 상태 존재

화면 라벨과 실제 원천 시각이 다를 수 있고 완료·취소·진행·재접수를 O/X로 축약할 기준 없음

정렬·필터·완료 건수 불일치, 실제 작업 시작 시각 오해

maintenance_order에 receivedAt, startedAt, completedAt, status를 명시. 화면 요구가 접수 시각을 ‘정비 일시’로 표시한다면 데이터 사전에도 그 사실 기록

R-OPS-002·003운영효율 평균·실제 작업시간

TB_EQUIPMENT_DAILY_OPERATION, TB_EQUIPMENT_MONTH_OPERATION, TB_WORKING_HOUR, TB_WORKING_TIME

일·월 집계와 작업시간 원천이 나뉘며 산식·시간 단위·근무시간 밖 처리 기준이 명세에 없음

월 평균 단순평균 오류, 비율과 실제 시간 불일치, 100% 초과

metric_dictionary에 산식·분자·분모·기준 단위 정의. API가 workingSeconds, availableSeconds, efficiencyRate를 함께 반환하고 0/미수신 구분

R-OPS-006·R-BAT-002다국어 명칭·지역 단위

TB_CODE_LANG는 LANG_CODE varchar(2). TB_SCHEDULE·TB_EQUIPMENT_ERROR_CODE는 EN/DE/ES 등 언어별 컬럼. USER에 LOCALE_CODE와 LANGUAGE 중복

지원 언어 추가마다 컬럼 변경. 지역 언어 변형, fallback, °C/°F·km/mile·L/h 변환 계약 부족

글로벌 확장 시 스키마 변경과 번역 누락 반복

BCP 47 locale과 translation_resource(entityType/entityId/fieldKey/locale/text) 도입. 수치는 canonicalValue+unitCode로 저장·전달 후 표시 단계 변환

R-HOME-001·002고객 동의·재판매 소유권

TB_EQUIPMENT, TB_COMPANY_EQUIPMENT, TB_EQUIPMENT_AGREE2, TB_COMPANY_CUSTOMER, TB_EQUIPMENT_HISTORY

현재 소유·관리 업체와 고객 동의·재판매 효력일·취소 이력의 기준 테이블이 분명하지 않음

미동의 차량 노출, 이전 고객 데이터 접근, 재판매 중복 반영

equipment_ownership_history와 equipment_consent를 별도 관리. sourceEventId+effectiveAt으로 멱등 처리하고 현재 관계는 이력에서 산출

R-SUP-001~004소모품 초기화·교환 완료

TB_SERVICE_SCHEDULE, TB_SERVICE_SCHEDULE_ACTION, TB_SCHEDULE

교환주기·누적시간·조치가 있으나 초기화 전후값·실행 역할·실제 교환일·관리 시작점의 원자적 저장 규칙 부족

중복 초기화, 사용량 역전, 누가 어떤 기준을 바꿨는지 추적 불가

supply_action에 before/after snapshot, actionType, performedBy, performedAt, exchangeDate, note, idempotencyKey 저장. 단일 트랜잭션 적용

페이지 공통업체·그룹·차량 변수 전달

프론트 라우트·Pinia persisted 상태에서 companyId, groupId, equipmentId 전달. TB_COMPANY·TB_GROUP·TB_EQUIPMENT 관계 사용

부모 대상 변경 시 종속 ID가 남거나 첫 번째 값으로 fallback 가능. URL ID는 권한 증명이 아님

다른 업체 차량 조회, 메뉴 이동 후 잘못된 대상 표시

navigation context 계약 고정. company 변경 시 group/equipment 초기화, group 변경 시 equipment 재검증. 서버는 token scope와 모든 ID 교차 검증

02 · CURRENT TABLE STRUCTURE

현재 테이블 구조의 공통 문제

개별 요구사항을 넘어 글로벌 운영과 장기 유지보수에 반복 영향을 주는 구조

01

사용자 모델 이원화

TB_USER와 TB_MEMBER, 설정·인증·토큰 테이블이 병렬 존재. 어떤 서비스가 어느 사용자를 기준으로 하는지 불명확

통합 user_account와 service membership 필요
02

권한 모델 분산

메뉴·업체·메뉴그룹·역할 테이블과 문자열 역할 목록 혼재. SITE_TYPE에 DEALER 포함 여부도 불일치

역할·권한·대상범위 정규화 필요
03

차량 식별자 중복

EQUIPMENT_ID, EQUIPMENT_ID_PP, EQUIPMENT_NUMBER, TERMINAL_ID, SAP ID가 존재하지만 기준 ID와 외부 ID 구분 부족

불변 내부 UUID와 외부 식별자 매핑 필요
04

오류 이벤트 중복

일반·납축·리튬 오류 테이블이 비슷한 필드를 반복하고 완료 의미가 다름

통합 이벤트 계약과 원천 유형 보존 필요
05

시간 데이터 혼재

datetime과 날짜·시간 문자열이 함께 존재하고 TIMEZONE_ID 길이 20/50/64, UTC_OFFSET 문자열도 혼재

UTC instant + IANA timezone 표준화 필요
06

다국어 확장 한계

2자리 언어코드, LOCALE_CODE와 LANGUAGE 중복, 언어별 고정 컬럼, locale 없는 메시지 템플릿

BCP 47 번역 리소스와 fallback 필요
07

단위·산식 정의 부족

값과 단위가 설명·문자열에 섞이고 운영효율·연비 산식이 테이블 명세만으로 확정되지 않음

지표 사전과 canonical unit 필요
08

상태·감사 규칙 불일치

USE_YN, REPAIR_YN, RESOLUTION_YN, CONFIRM·CHECK·RESULT 시각의 의미가 업무별로 다름

명시적 상태 머신과 변경 이력 필요
09

문서 연결 부족

TB_FILE은 일반 파일 메타만 있고 오류·정비·언어·버전·권한 관계가 없음

업무 문서 관계와 접근정책 필요
10

백업·구버전 테이블 혼재

165개 목록에 BAK, OLD, DEV, 날짜 백업, 테스트 테이블이 운영 후보와 함께 노출

활성 스키마 카탈로그와 폐기 정책 필요
11

오타·중복 컬럼

HISTROY, ACCOUT, COMULATIVE/CUMULATIVE 등 이름 오류와 유사 컬럼 중복

데이터 사전·호환 뷰·단계적 정리 필요
12

업무 식별자 계약 부재

오더·통지·수리 ID·LINQ_NO를 Claim으로 볼 수 있는지 명세만으로 판단 불가

외부 시스템 식별자 유형과 원천 계약 필요

03 · GLOBAL TARGET STRUCTURE

글로벌 전환을 위한 목표 데이터 구조

기존 테이블을 한 번에 폐기하지 않고 API 표준화 계층과 신규 기준 테이블을 먼저 도입

IDENTITY

사용자·조직·권한

user_account → organization_membership → role_permission → resource_scope

→
ASSET

차량·소유·동의

equipment → equipment_identifier → ownership_history → consent

→
EVENT

오류·정비·소모품

fault_event / maintenance_order / supply_action + status_history

→
GLOBAL

언어·시간·단위

translation_resource + IANA timezone + canonical value/unit

공통 요청 컨텍스트

{
  service: "fleet | dealer",
  locale: "ko-KR",
  timezone: "Asia/Seoul",
  companyId: 1933,
  groupId: 1948,
  equipmentId: "FBA34_224030249",
  periodType: "day | week | month | custom",
  startAt: "UTC ISO-8601",
  endAt: "UTC ISO-8601"
}

company/group/equipment는 선택 상태. 실제 접근 권한은 인증 토큰과 서버 관계 테이블로 검증

공통 응답 원칙

{
  data: {...},
  unitMeta: {...},
  displayLocale: "ko-KR",
  timezone: "Asia/Seoul",
  sourceStatus: "RECEIVED | MISSING | ESTIMATED",
  permissions: ["fault.view", "document.download"],
  traceId: "..."
}

0과 미수신, 원본과 추정, 조회와 조치 권한을 응답에서 분리

권장 적용 순서

  1. 1. 기준 확정Claim 관계, 오류 상태, 운영효율 산식, 사용자설정 조회 범위 확정
  2. 2. API 계약공통 컨텍스트·오류·단위·null·권한 DTO 정의
  3. 3. 정규화 테이블사용자/권한, 식별자, 번역, 문서, 상태 이력 신규 도입
  4. 4. 호환 계층기존 TB_* 원천을 신규 DTO로 매핑하는 view/adapter 구축
  5. 5. 데이터 정리중복·오타·백업 테이블 격리와 데이터 품질 검증
  6. 6. 지역 검증언어·타임존·주 시작일·단위·권한 정책 국가별 테스트

우선 확인이 필요한 네 가지

  • 사용자설정 조회는 실제 업무상 어느 기간까지 필요한지
  • 수리 ID·AUFNR·QMNUM 중 Claim에 해당하는 식별자가 무엇인지
  • 차량·엔진·배터리 오류의 현재/과거·완료 판정 기준이 무엇인지
  • 플릿과 딜러가 볼 수 있는 정비 상세 필드와 실행 가능한 조치가 무엇인지
현재 테이블 구조 문제만 보기개발 아틀라스로 돌아가기

분석 기준일 2026-08-26 · 물리 DB와 외부 연동 실데이터는 별도 확인 필요
