CURRENT DATABASE / API STRUCTURE REVIEW

현재 테이블로 플릿·딜러 API를
효율적으로 만들 수 있는가?

판정원천 데이터 재사용은 가능하지만, 현재 테이블을 그대로 직접 조회해 플릿·딜러 API를 만드는 구조는 비효율적

화면별 데이터는 존재하나 사용자·권한·차량 관계·오류·정비·다국어 기준이 분산되어 있음. 서비스마다 같은 데이터를 다른 조건과 조인으로 재구성하게 되어 API 중복과 정합성 문제가 커짐

데이터 보유양호

차량·운행·오류·정비·소모품 원천 존재

플릿·딜러 공통화낮음

서비스 구분·권한·필드 노출 기준 분산

API 유지보수성주의

화면별·원천별 API와 조건 분기 증가

SQL 실행 성능판정 불가

백엔드 쿼리·인덱스·실행계획 미제공

중요이 문서는 구조적 효율을 판정. 실제 응답속도·DB 부하는 SQL, 인덱스, 통계정보, 실행계획을 추가 확인해야 확정 가능

01 · CURRENT CALL STRUCTURE

현재 플릿·딜러 호출 구조에서 생기는 문제

왜 비효율적인가

  1. 같은 화면도 서비스별 조건이 달라짐플릿은 소속 그룹, 딜러는 관리 업체·판매 관계를 기준으로 하므로 WHERE·JOIN·응답 필드가 달라짐
  2. 서비스 구분이 API 계약에 명확하지 않음딜러 화면도 `/fleet/*` 경로와 공통 모듈을 사용. 재사용 자체는 가능하지만 책임과 권한 경계가 불분명
  3. 권한을 확인하려면 여러 모델을 해석해야 함USER/MEMBER와 메뉴·업체·역할 테이블이 분산되어 API마다 접근 범위를 다시 계산할 가능성
  4. 통합 요구를 원천 테이블이 지원하지 않음차량·엔진·배터리 오류를 한 화면에 표시하려면 서로 다른 상태 의미를 API에서 매번 병합해야 함
  5. 화면별 DTO가 DB 컬럼에 끌려감업무 용어·식별자·단위가 표준화되지 않아 프론트와 API에 예외 처리와 변환 코드가 늘어남

02 · STRUCTURAL PROBLEMS

현재 테이블 구조 문제를 한눈에 보기

문제 테이블, API 영향, 실제 발생 가능한 결과를 직접 연결

구조 문제확인된 테이블·필드플릿·딜러 API 영향결과심각도

사용자 체계가 두 개

TB_USER / TB_MEMBER와 각각의 설정·인증·토큰 테이블

플릿·딜러 로그인 사용자를 어느 기준으로 권한 계산할지 API마다 달라질 수 있음

사용자 누락·중복, 서로 다른 메뉴·차량 접근 결과치명

권한 구조가 여러 테이블로 분산

TB_MENU, TB_MENU_ROLE, TB_COMPANY_MENU, TB_COMPANY_MENU_GROUP, TB_COMPANY_ROLE, TB_USER_ROLE

메뉴 표시, 데이터 조회, 상세 필드, 수정 실행 권한이 하나의 규칙으로 연결되지 않음

화면은 숨겨졌지만 API 직접 접근 가능 또는 정상 사용자 차단치명

SITE_TYPE 정의 불일치

TB_MENU: ADMIN/FLEET/RENTAL/APP · TB_COMPANY_MENU: MEMBER/DEALER 포함

딜러 메뉴가 기본 메뉴 정의와 업체별 메뉴 정의에서 다르게 해석될 가능성

딜러 메뉴·권한 설정의 예외 분기 증가높음

역할·그룹 ID가 문자열 목록

TB_MENU.DENY_ROLE_ID varchar(200) · TB_USER.GROUP_SET_LIST varchar(700)

정규 JOIN 대신 문자열 검색·파싱 필요. 변경·검증·인덱스 사용이 어려움

권한 누락과 느린 조건 검색, 잘못된 부분 일치높음

차량 기준 ID가 불명확

EQUIPMENT_ID, EQUIPMENT_ID_PP, EQUIPMENT_NUMBER, TERMINAL_ID, SAP 관련 ID

화면 이동·API·외부 연계에서 어떤 ID가 불변 기준인지 명확하지 않음

차량이 바뀌거나 재등록될 때 이력 단절·잘못된 차량 조회치명

소유·관리·동의 관계가 분산

TB_EQUIPMENT, TB_COMPANY_EQUIPMENT, TB_EQUIPMENT_AGREE2, TB_COMPANY_CUSTOMER, TB_EQUIPMENT_HISTORY

플릿 소속, 딜러 관리, 현재 고객, 동의 여부를 조회할 기준 관계가 한곳에 없음

미동의·이전 고객 차량 노출, 전체 카운트 불일치치명

오류 테이블이 원천별로 중복

TB_EVENT_ERROR / TB_EVENT_BM_ERROR / TB_EVENT_LI_ERROR / TB_EQUIPMENT_ERROR

차량 에러 통합 API가 서로 다른 컬럼·완료 기준을 병합해야 함

중복 건수, 현재/과거 오판, 배터리·차량 분류 오류치명

정비 식별자 관계가 없음

AUFNR, QMNUM, ORDER_NO, LINQ_NO는 있으나 Claim 명칭 필드 없음

정비 이력 API에 Claim을 표시하려면 어떤 값을 써야 할지 확정 불가

임의 Claim 표기, SAP 정합성 오류높음

완료·현재 상태 정의가 제각각

USE_YN, REPAIR_YN, RESOLUTION_YN, CONFIRM·RESULT·CHECK 시각

서비스 카운트와 목록 필터가 서로 다른 완료 판정을 사용할 수 있음

KPI와 상세 목록 건수 불일치높음

다국어 모델이 혼합

TB_CODE_LANG의 2자리 LANG_CODE, 언어별 고정 컬럼, USER의 LOCALE_CODE와 LANGUAGE

메뉴·오류코드·소모품·알림마다 번역 조회 방식과 fallback이 달라짐

신규 국가 추가 시 컬럼·API·프론트 동시 수정높음

시간대·날짜 형식이 혼합

TIMEZONE_ID varchar(20/50/64), UTC_OFFSET 문자열, datetime과 날짜·시간 문자열

일·주·월 집계와 발생일시 경계가 사용자·업체·차량 기준으로 달라질 수 있음

날짜별 그래프와 카운트가 지역마다 달라짐높음

백업·구버전·오타 테이블 혼재

BAK/OLD/DEV/날짜 테이블, HISTROY·COMULATIVE/CUMULATIVE 등

개발자가 기준 테이블과 기준 컬럼을 잘못 선택할 위험

동일 기능이 서로 다른 원천을 조회하는 유지보수 문제중간

03 · EFFICIENT API DIRECTION

테이블을 전부 갈아엎지 않고 API 효율을 높이는 방법

피해야 할 방식

플릿·딜러 API가 원천 테이블을 각각 직접 조합

각 화면에서 USER/MEMBER, 권한, 업체·그룹·차량, 오류 원천을 별도 JOIN·분기

화면 수 × 서비스 수 × 원천 테이블 수만큼 예외 증가
권장 방식

공통 도메인 조회 계층 뒤에 플릿·딜러 정책 적용

기존 테이블은 adapter/view로 읽고, 표준 차량·권한·오류·정비 DTO를 만든 뒤 서비스별 범위와 필드만 적용

최종 답변

현재 테이블만으로도 플릿·딜러 화면 데이터는 만들 수 있음. 그러나 원천 테이블을 각 API가 직접 조합하는 방식은 서비스가 늘수록 중복과 오류가 커짐. 기존 테이블 위에 공통 도메인 조회 계층 + 플릿·딜러 정책 계층을 두는 방식이 가장 현실적이고 효율적

전체 요구사항·테이블 진단 보기개발 아틀라스로 돌아가기분석 기준: 테이블 명세·현재 로컬 프론트 API 모듈. 백엔드 SQL·실행계획 별도 확인 필요
